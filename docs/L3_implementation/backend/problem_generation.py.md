# `backend/problem_generation.py`

## 目的・役割

`backend/app.py` の `POST /generate-problems` エンドポイント(issue #138)が呼び出す、PDF/LaTeX を一切生成しない「問題データのみ生成」ロジック。PDF/プレゼンテーション層(`backend/three_layer_renderer.py`)とは責務を分離した、データ層のモジュール。issue #166「データ層とプレゼンテーション層の分離」の最初の実装であり、issue #167-#173 の native sub-issue 群で全コマンド対応を完了した。当初は `nuts_calc.py`(ReportLab)/`nuts_calc_tex.py`(LaTeX)の2レンダラーに対応していたが、`nuts_calc.py` は issue #232 で削除され、以降 `nuts_calc_tex.py` のみを呼び出す。

issue #359(親 #357)で、このモジュールは2層に分離された:

- **共有生成層** `generate(command_type, params, count, start_index) -> list[<problem dataclass>]`(`problem_generation.py:99`): パラメータ検証・正規化を所有し、`nuts_calc_tex.py` の `generate_*` が返す生の problem dataclass のリストをそのまま返す(dict 化もレスポンス envelope 整形もしない)。将来 `three_layer_renderer._generate_*_pdf` builder が問題解決に使う唯一の場所になる(その移行は issue #360-#363。現時点でどの builder もまだ呼んでいない)。
- **薄い dict ラッパー** `generate_problems(params, renderer_name=None) -> list[dict]`(`problem_generation.py:70`): `POST /generate-problems` 用。`generate(...)` を呼び、各 dataclass を JSON フレンドリな dict へ直列化し、レスポンス契約が持つ計算プロパティ(`ope` の curated な `OpeProblemData` 形、`compare` の `relation`、`frac2dec`/`dec2frac` の `decimal_display`)だけを注入する。

`command_type == 'ope'`(素の2項四則演算 + issue #168 の `--use-parentheses`/`--missing-value`/`--terms`系(`terms`/`terms_min`/`terms_max`/`mixed_operators`)3亜種)に加え、issue #169 で `com`/`99`/`aBc`/`squ`/`pi`、issue #170 で `frac`/`mixed`、issue #171 で `compare`、issue #172 で `evenodd`/`multiples`/`divisors`/`lcm`/`gcd`、issue #173 で `simplify`/`commondenom`/`frac2dec`/`dec2frac`/`divfrac`、issue #346 で `approx`(概数)を実装した。`100`(100マス加算表)も issue #228 で対応したが、`_COMMAND_GENERATORS` や `{"problems": [...]}` envelope は経由せず、専用関数 `generate_hundred_square_table()` が単一テーブル用の `{"table": {...}}` envelope を返す(下記「`100` を別 envelope で対応している理由」参照)。それ以外の `command_type` は `ValueError` を送出する。

## 動作の概要

- `generate_problems(params, renderer_name=None)`(公開関数、`problem_generation.py:70`): `renderer_name` 省略時は `renderer_config.get_renderer_name()` で解決(`latex` 以外を fail-fast させるためだけに使う。値自体は未使用)。`num`(生成する問題数)が正の整数でない場合は `command_type` に関わらず `ValueError("num must be a positive integer")` を送出する。以降は `generate(command_type, params, num, 1)` を呼び、返った dataclass のリストを `_serialize_problems(command_type, params, problems)` で dict 化して返すだけの薄いラッパー(issue #359)。`100` の targeted `ValueError` も `generate()` から伝播する(分岐重複を除去)。
- `generate(command_type, params, count, start_index)`(公開関数、`problem_generation.py:99`、issue #359): 共有生成層の入口。`count` が正の整数でなければ `ValueError("count must be a positive integer")`。`command_type == '100'` は `_COMMAND_GENERATORS` の list 契約に合わないため、`generate_hundred_square_table()` を案内する targeted な `ValueError` を送出する(エンドポイントは `100` をここへ到達させる前に `generate_hundred_square_table` へルーティングするので、この分岐に当たるのは直接呼び出す caller だけ)。それ以外は `_COMMAND_GENERATORS`(`command_type` 文字列 → 生成関数の dict、`problem_generation.py:909`)を引き、未登録の `command_type` は issue #166 の「not yet supported」`ValueError` を送出する。登録済みの場合は `generator(params, count, start_index)` を呼び、`nuts_calc_tex.py` の生の problem dataclass リストを返す(`_dataclass_to_dict` は通さない)。
- `_COMMAND_GENERATORS`(`problem_generation.py:909`)は20 `command_type`(`ope` を含む)をカバーする。各 generator のシグネチャは `(params, count, start_index) -> list[<dataclass>]`。`ope` は `_generate_ope`(`problem_generation.py:140`)が担当し、`_determine_ope_variant()` の判定に応じて `tree`/`missing_value`/`multi_term`/素の2項へディスパッチする。`100` はこのテーブルに載らない(上記 targeted `ValueError` + `generate_hundred_square_table()` 経路)。
- `_serialize_problems(command_type, params, problems)`(`problem_generation.py:871`、issue #359)は `generate(...)` の dataclass を `{"problems": [...]}` envelope の dict に変換する:
    - `command_type == 'ope'` → `_serialize_ope_problems(params, problems)`(`problem_generation.py:810`)。素の2項は `nuts_calc_tex.OpeProblem` インスタンスが返るので、curated な `OpeProblemData` 形(`c` → `"result"`、固定サブセットのフィールド、`--decimal-remainder`/`--divide-through` モードでのみ `result_decimal_places` キー追加、`intermediate=True` でのみ `intermediate_memo` キー追加)へ手動マップする。`tree`/`missing_value`/`multi_term` 亜種は各自の dataclass が返り、汎用 `_dataclass_to_dict()` を通る(issue #359 以前と同一挙動)。
    - `command_type in {'compare', 'frac2dec', 'dec2frac'}` → `_dataclass_to_dict()` + `_RESPONSE_PROPERTY_INJECTORS`(`problem_generation.py:864`)の注入関数で派生 `@property`(`compare` の `relation`、`frac2dec`/`dec2frac` の `decimal_display`)を明示キーとして足す。
    - それ以外 → `[_dataclass_to_dict(problem) for problem in problems]`。

> 注(issue #359): 以下のコマンド別の記述で「`_dataclass_to_dict()` で dict 化してから返す」「`relation`/`decimal_display` を明示キーで追加する」とあるのは、issue #359 以降は各 `_generate_*_problems` generator ではなく `_serialize_problems`(上記)が行う。generator 自体はパラメータ検証と `nuts_calc_tex.generate_*(...)` 呼び出し(`num` → `count`、ハードコードの `1` → `start_index`)だけを行い、生の dataclass リストを返す。検証ロジックの内容自体は変わっていない。
- `com`/`99`(kuku)/`aBc`/`squ`/`pi` はそれぞれ `_generate_com_problems`/`_generate_kuku_problems`/`_generate_abc_problems`/`_generate_squ_problems`/`_generate_pi_problems` が対応する。`nuts_calc_tex.py` の同名 `generate_*_problems()` を直接呼び出すだけの薄いラッパーで、レンダラー分岐を持たない(下記「reportlab 分岐は持たない」参照)。`a_value` が必須なコマンド(`com`/`99`/`squ`/`pi`)は未指定を明示的な `ValueError` で拒否し(いずれも `nuts_calc_tex.py` の `_init()` が CLI 引数に対して行うバリデーションと同じ制約をリクエストパラメータに対して再現したもの)、`com` はさらに `nuts_calc_tex.MIN_COMPLEMENT_TARGET` 未満の `a_value` を拒否する。`com` のこの2チェックは公開関数 `validate_com_target(a_value)` に切り出されており、`_generate_com_problems` と `backend/app.py`(`_generate_com_pdf`)の双方から呼ばれる共有バリデータになっている(issue #237、下記「共有バリデータ `validate_com_target()` を切り出した理由」参照)。`99` の必須チェックも同じパターンで `validate_kuku_a_value(a_value)` に切り出されており、`_generate_kuku_problems` と `backend/app.py`(`_generate_kuku_pdf`)の双方から呼ばれる(issue #208、`validate_com_target()` の抽出パターンをそのまま踏襲)。`squ` の必須チェック(下限なし)も同じパターンで公開関数 `validate_squ_start(a_value)` に切り出されており、`_generate_squ_problems` と `backend/app.py`(`_generate_squ_pdf`)の双方から呼ばれる(issue #209、`validate_com_target` のデデュープパターンを踏襲)。`pi` の必須チェック(下限なし)も同じパターンで公開関数 `validate_pi_start(a_value)` に切り出されており、`_generate_pi_problems` と `backend/app.py`(`_generate_pi_pdf`)の双方から呼ばれる(issue #210、issue #237 が確立した「共有バリデータを抽出して両側から呼ぶ」規約に最初から従って実装)。`99`/`squ`/`pi` の `descend`/`shuffle` はどちらも既定 `False`。いずれも `_dataclass_to_dict()` で dict 化してから返す(`problem_generation.py:288-333`)。
- `frac`/`mixed`(issue #170)はそれぞれ `_generate_frac_problems`/`_generate_mixed_problems` が対応する。この2コマンドはエンドポイントが argparse を経由しないため、`nuts_calc_tex.py` の `_init()` が CLI 引数に対して行うバリデーションをリクエストパラメータに対して再現している(`ope` 亜種の `_determine_ope_variant()` と同じパターン、下記「`frac`/`mixed` の CLI バリデーションを再現している理由」参照)。両コマンド共通の `numerator_digits`/`denominator_digits` 範囲チェックは `_validate_fraction_digits()` に、`reducible_mode` の operator 制約チェックは `_validate_reducible_operators()` に共通化している(`problem_generation.py:336-353`)。
    - `_generate_frac_problems`: `same_denominator`×`different_denominators` 排他、`proper_operands` 指定時の `numerator_digits <= denominator_digits` 制約、`a_fraction_form`/`b_fraction_form` が `'proper'` でない場合の operator(`['add']`/`['sub']` のみ)・`'improper'` 不可制約、`reducible_mode` 指定時の operator(`{mul,div}` の部分集合)制約を検証したうえで `nuts_calc_tex.generate_fraction_problems(...)` を呼び出す(`problem_generation.py:355-393`)。
    - `_generate_mixed_problems`: `decimal_places` 範囲チェック、`_determine_mixed_terms()`(`terms`/`terms_min`/`terms_max`/`mixed_operators` から `nuts_calc_tex.resolve_term_range(..., use_parentheses=False)` で範囲を解決 — `mixed` に `--use-parentheses` 相当のオプションはないため常に `False` を渡す)、`reducible_mode` 指定時の operator 制約・`terms` 系との併用禁止・`{a_kind, b_kind}` が `{('fraction',), ('int',)}` である制約を検証したうえで `nuts_calc_tex.generate_mixed_problems(...)` を呼び出す(`_determine_mixed_terms`: `problem_generation.py:396-417`、`_generate_mixed_problems`: `problem_generation.py:420-458`)。
- `compare`(issue #171)は `_generate_compare_problems` が対応する。`numerator_digits`/`denominator_digits` 範囲チェックは `frac`/`mixed` と同じ `_validate_fraction_digits()` を再利用する。`decimal_places`(既定1)の範囲チェックは `mixed` と同じ値域(`MIN_DECIMAL_PLACES`〜`MAX_DECIMAL_PLACES`)。`a_kind`/`b_kind`(既定 `['fraction']`、`mixed` と異なり compare は分数のみが既定 — 後方互換のため)を解決したうえで、`comparison_pattern`(既定 `'different-denominators'`)が非既定でありながら `a_kind`/`b_kind` のどちらかが `['fraction']` でない場合は `ValueError` にする(`nuts_calc_tex.py` の `_init()` と同じ制約、下記「`compare` の kind 混在バリデーションを再現している理由」参照)。`nuts_calc_tex.generate_fraction_comparison_problems(...)` を呼び出した後、各 `FractionComparisonProblem` を `_dataclass_to_dict()` で dict 化し、`relation`(`@property`、`FractionComparisonProblem` の実フィールドではない)を明示的に追加してから返す(`intermediate_memo` と同じ「計算プロパティは明示キーで追加」パターン、`problem_generation.py:461-505` 付近)。
- `evenodd`/`multiples`/`divisors`(issue #172)はそれぞれ `_generate_evenodd_problems`/`_generate_multiples_problems`/`_generate_divisors_problems` が対応する。3コマンドとも `a_min`/`a_max`(既定1/9、`a_digits` ショートハンドは非対応 — `nuts_calc_tex.py` の `_init()` 側でもこの3コマンドは `DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれていないため)から `nums_a` を組み立て、`nuts_calc_tex.generate_evenodd_problems`/`generate_multiples_problems`/`generate_divisors_problems` を直接呼び出す。`multiples`/`divisors` は `a_min < 1` を `ValueError` で拒否する(`nuts_calc_tex.py` の `_init()` と同じ制約)。`multiples` はさらに `multiples_count`(既定 `nuts_calc_tex.DEFAULT_MULTIPLES_COUNT`)が `nuts_calc_tex.MIN_MULTIPLES_COUNT` 未満なら拒否する。`lcm`/`gcd`(issue #172)は共有ヘルパー `_generate_number_pair_problems(params, num, compute)` の薄いラッパー `_generate_lcm_problems`/`_generate_gcd_problems`(`compute=math.lcm`/`math.gcd`)が対応する。この2コマンドは `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS`(issue #230)に含まれるため、`resolve_digit_count_range()` を再利用して `a_digits`/`b_digits`(または明示 `a_min`/`a_max`/`b_min`/`b_max`)から範囲を解決したうえで `nuts_calc_tex.generate_number_pair_problems(compute, nums_a, nums_b, num, 1)` を呼び出す(下記「`lcm`/`gcd` で生成関数を1つ共有している理由」参照)。いずれの5コマンドも `_dataclass_to_dict()` で dict 化してから返す(`problem_generation.py:507-565`)。
- `simplify`/`commondenom`/`frac2dec`/`dec2frac`/`divfrac`(issue #173)はそれぞれ `_generate_simplify_problems`/`_generate_commondenom_problems`/`_generate_frac2dec_problems`/`_generate_dec2frac_problems`/`_generate_divfrac_problems` が対応する。いずれも `nuts_calc_tex.py` の同名 `generate_*_problems()` を直接呼び出すだけの薄いラッパーで、新規のドメインロジックは持たない。`simplify`/`commondenom`/`frac2dec` の3コマンドは `frac`/`mixed`/`compare` と同じ `_validate_fraction_digits()` で `numerator_digits`/`denominator_digits`(既定1)を検証する。`dec2frac` は digit 引数を取らず(`nuts_calc_tex.generate_dec2frac_problems(order, start_index)` のみ)、`_init()` 側の固定レンジ(`DEC2FRAC_MIN_DECIMAL_PLACES`〜`MAX_DECIMAL_PLACES`)をそのまま使う。`divfrac` は `lcm`/`gcd` と同じ `resolve_digit_count_range()`(`a_digits`/`b_digits` ショートハンド対応)で `a_min`/`a_max`/`b_min`/`b_max` を解決し、`b_min < 1` を `ValueError` で拒否する(`nuts_calc_tex.py` の `_init()` と同じ制約、`divfrac` は0除算を避けるため `b_min>=1` が必須)。`frac2dec`/`dec2frac` は `Frac2DecProblem`/`Dec2FracProblem` の `decimal_display`(`@property`、`scaled_numerator`+`decimal_places` から `format_decimal_value()` で組み立てる整形済み小数文字列)を `compare` の `relation` と同じ「計算プロパティは明示キーで追加」パターンで dict に追加する。いずれも `_dataclass_to_dict()` で dict 化してから返す(`problem_generation.py:568-620`)。
- `approx`(概数、issue #346)は `_generate_approx_problems` が対応する。他の非-`ope` ラッパーと同じく薄いラッパーだが、`nuts_calc_tex.resolve_approx_params(kind=..., round_method=..., round_place=..., sig_digits=..., quotient_decimal_places=..., dividend_decimal_places=..., operator=<operator[0] or None>, a_min/a_max/b_min/b_max=...)` を呼んでパラメータ検証・kind別デフォルト解決・feasibility 判定を委譲し、返った `ApproxParams` で `nuts_calc_tex.generate_approx_problems(...)` を呼ぶ。`resolve_approx_params` は `POST /generate-pdf` の `_generate_approx_pdf`([[three_layer_renderer.py]])も呼ぶ共有関数で、`_init()` を経由しないこの2経路が同じ既定・同じ拒否になる(不正な `--kind` の組合せ・estimate の operator 欠落・実行不能レンジは `ValueError` → HTTP 500)。`ApproxProblem` は `index`/`kind`/`expr_tex`/`answer_tex`/`expr_plain`/`answer_plain` の単純フィールドのみで `_dataclass_to_dict()` を素通りする。`approx` は `DIGIT_COUNT_SHORTHAND_COMMANDS` 外のため `resolve_digit_count_range()` は使わず `a_min`/`a_max`/`b_min`/`b_max` を直接読む。
- `resolve_hundred_square_axes(params)`(公開関数、issue #229、`problem_generation.py:247-283`)は `100` の (left, top) 軸値リストを解決する共有ヘルパー。`resolve_digit_count_range()`（`lcm`/`gcd`/`divfrac` と同じ #230 の共有リゾルバ、`a_digits`/`b_digits` ショートハンドまたは明示 `a_min`/`a_max` / `b_min`/`b_max`、既定 `DEFAULT_A_MIN`〜`DEFAULT_A_MAX`=1〜9）で a/b 軸のレンジを解決し、各軸のレンジが `_HUNDRED_SQUARE_MIN_AXIS_VALUES`(= `nuts_calc_tex.HUNDRED_SQUARE_SIZE // nuts_calc_tex.HUNDRED_SQUARE_SAMPLE_REPEAT_FACTOR` = 5)未満なら説明的な `ValueError` を送出する(`nuts_calc_tex.sample_hundred_square_values()` の素の `random.sample` ValueError を先回りして分かりやすくするため)。`(nums_left, nums_top)` を返す。`generate_hundred_square_table()`(`POST /generate-problems`、issue #228)と `backend/app.py` の `_generate_hundred_square_pdf()`(`POST /generate-pdf`、issue #229)の両方から呼ばれ、2エンドポイントが軸解決と最小値ルールを1箇所で同一に扱う。
- `generate_hundred_square_table(params)`(公開関数、issue #228、`problem_generation.py:285-324`)は `100` 専用。`_COMMAND_GENERATORS` にも `generate_problems()` の list 契約にも乗らず、`backend/app.py` の `/generate-problems` ハンドラが `command_type == '100'` のときだけ直接呼ぶ。軸解決は `resolve_hundred_square_axes(params)` へ委譲し(issue #229 で抽出、以前は本関数にインライン)、`nuts_calc_tex.generate_hundred_square(nums_left, nums_top)` を呼び、`{"table": {"left_values": [...10], "top_values": [...10], "answers": [[...10] x10]}}`(`answers[r][c] == left_values[r] + top_values[c]`)を返す。`num` は全 command 共通の入力検証のためエンドポイントが必須にしているが、単一テーブルには意味を持たず無視される(CLI が `100` で `rows`/`columns`/`with_bottom_answer` を無視するのと同じ)。
- `_determine_ope_variant(params)` で `use_parentheses`/`missing_value`/`terms`系フラグから対象亜種(`'tree'`/`'missing_value'`/`'multi_term'`/`None`)を判定する。この関数はエンドポイントが argparse を経由しないため、`nuts_calc_tex.py` の `_init()` が CLI 引数に対して行う相互排他バリデーション(`--missing-value` は `--use-parentheses`/`--terms`系と併用不可)と `resolve_term_range()` による term数レンジのフロー・クランプ(`--use-parentheses` はフロア3、それ以外はフロア2、上限は `MAX_OPE_TERMS`)を、リクエストパラメータに対して再現する(`problem_generation.py:93-137`)。
- 亜種が判定された場合、以下へディスパッチする(`_generate_ope`、`problem_generation.py:140`。issue #359 以前は `generate_problems()` 内の `_generate_ope_problems()` 早期分岐だったが、共有 `generate()` 層への分離で `_COMMAND_GENERATORS["ope"]` に登録した generator になった)。issue #232 以前は `renderer_name == 'reportlab'` をここで即座に `ValueError` としていたが(`nuts_calc.py` に亜種の対応実装がなかったため)、`nuts_calc.py` 自体の削除に伴いこのチェックごと削除した(下記「`ope` の reportlab 分岐を削除した理由」参照):
    - `'tree'` → `_generate_tree_ope_problems`: `nuts_calc_tex.generate_tree_ope_problems(...)` を直接呼び出し、`TreeOpeProblem` dataclass のリストを返す。`params.get("nontrivial_division", False)` を `bool(...)` 化して末尾の位置引数(`result_max` の1つ後ろ)として転送する(issue #342、`a_multiple`/`b_multiple` と同じ「制約チェックを追加せず寛容にフォワード」パターン)。frontend `g4-parentheses` プリセットが立てるフラグで、`nuts_calc_tex` 側が「有効時は除算を必ず含み、割る数・商とも2以上」を保証する。条件(`mixed_operators` + div 演算子)が揃わなければ `nuts_calc_tex` 側で静かに no-op。
    - `'missing_value'` → `_generate_missing_value_problems`: `nuts_calc_tex.generate_missing_value_problems(...)` を直接呼び出し、`MissingValueProblem` dataclass のリストを返す。
    - `'multi_term'` → `_generate_multi_term_ope_problems`: `nuts_calc_tex.generate_multi_term_ope_problems(...)` を直接呼び出し、`MultiTermOpeProblem` dataclass のリストを返す。

- 同様に `_generate_ope_problems_latex` は `bool(params.get("divide_through", False))` を `nuts_calc_tex.generate_ope_problems(...)` にキーワード引数として渡す(issue #349、`decimal_remainder` の直後)。同2プリセットの 余り設定「わり進み」= 商が終わるまで割り進む 用。制約チェックは追加しない(終端する商のペアの空レンジ fail-fast は `calc_div_divide_through` の `ValueError`。`isLivePreviewSupported()` は `divide_through` を素の2項 `ope` として通す)([[nuts_calc_tex.py]] の `### ope --divide-through` 参照)。

- `a_digits`/`b_digits`(桁数指定のショートハンド、issue #230 で `a_value`/`b_value` から分離。旧経緯は下記「`-a/--a-value` の桁数解釈を `--a-digits`/`--b-digits` へ分離した理由」参照)は `resolve_digit_count_range()`(`problem_generation.py` 内、`nuts_calc_tex.set_min_max_value()` を経由)で `a_min`/`a_max`/`b_min`/`b_max` に変換する。指定がなければ `a_min=1`/`a_max=9`/`b_min=1`/`b_max=9`(CLIのデフォルトと同値)を使う。この解決は3亜種の生成関数でも共通利用する。`a_value`/`b_value` は `ope` では一切読まれない(`com`/`99`/`squ`/`pi` 専用の値そのものフィールド)。
- `intermediate=True` の場合(素の2項 `ope` のみ)、`operator == ['mul']` かつ `b_max <= nuts_calc_tex.INTERMEDIATE_SINGLE_DIGIT_MAX`(値は9)であることを検証し、`_init()` の CLI バリデーションと同じ制約を(`exit(1)` ではなく)`ValueError` として再現する。

## 重要な設計判断とその理由

### 生成層 `generate()` とレスポンス直列化を分離した理由(issue #359、親 #357)

`_generate_*_problems` は元々「パラメータ解決/検証 → `nuts_calc_tex.generate_*(...)` 呼び出し → `_dataclass_to_dict()`(必要なら `relation`/`decimal_display` 注入)」を1関数で行っていた。同じ「パラメータ解決/検証 → `nuts_calc_tex.generate_*(...)`」は `three_layer_renderer.py` の各 `_generate_*_pdf` builder にも重複して書かれており(`_generate_frac_pdf` と `_generate_frac_problems` が同じ `generate_fraction_problems` の手前でそれぞれ独自に検証している等)、#357 の `/mtg`(2026-09-04)でこの重複の解消が合意された。

issue #359 はその第一歩として、dict 直列化・レスポンス envelope 整形を含まない共有 `generate(command_type, params, count, start_index) -> list[<dataclass>]` を切り出し、パラメータ検証/正規化をこの層に集約した。`generate_problems()` は `generate()` + `_serialize_problems()` の薄いラッパーに縮小した。`nuts_calc_tex.py` の `generate_*` 関数と dataclass は一切変更しない(共有層はその上の薄い統合層)。

- `count`/`start_index` を引数化した(旧 `_generate_*_problems` は `num` を取り `start_index=1` をハードコードしていた)。builder が `rows*columns` 分を複数ページに分けて採番するため、`start_index` の可変化が P2 移行の前提になる。
- レスポンス固有の後処理(`ope` の `OpeProblemData` 手動マップ、`compare`/`frac2dec`/`dec2frac` の `@property` 注入)は `_serialize_problems`/`_serialize_ope_problems`/`_RESPONSE_PROPERTY_INJECTORS` に集約した。これらは `/generate-problems` の JSON 契約であって生成ロジックではないため、共有層には置かない(#357 `/mtg` の「presentation は renderer 層の `command_type` キー registry に残す」方針と整合)。
- `three_layer_renderer._generate_*_pdf` と `_generate_review_pdf` は issue #359 では未変更。共有層は `POST /generate-problems` 経由でのみ exercise される。builder の移行は #360-#363(P2、群1〜4を直列)。
- `POST /generate-problems` のレスポンス(envelope・キー)は既存の全 valid リクエストで不変(既存の `test_problem_generation.py` 全 test が無変更で green。回帰ガードとして機能させる)。`generate()` の新公開契約(dataclass を返す・`count` 検証・`100` targeted error 等)は追加 test でカバーする。
- 将来 `/generate-pdf` と `/generate-problems` で strictness が食い違う箇所は、共有層が厳格側(`/generate-pdf`)に合わせる方針が #357 `/mtg` で合意されているが、issue #359 時点では builder 未移行のため、両者が既に同じ共有ヘルパー(`resolve_digit_count_range` 等)でパラメータを解決している範囲に留まり、実挙動の差分は発生していない。

### サブプロセス+`--csv`読み取りではなく、プロセス内直接呼び出しを選んだ理由

当初は `--csv` フラグを付けてサブプロセス実行し、生成された PDF を破棄して CSV だけ読み取る案を検討したが、「データ層とプレゼンテーション層を完全に分離したい」という将来方針(issue #166)に反する(PDFを一度実際に生成してから捨てる無駄が残り、CSVの列構成もコマンドごとにバラバラで意味づけできない)ため却下した。`get_operation_data()`/`generate_ope_problems()` がどちらも PDF/LaTeX 非依存の純粋関数だったため、プロセス内直接呼び出しが可能だった。

### `set_min_max_value()` の参照元(issue #232 で `nuts_calc_tex.py` へ切替)

`nuts_calc.py`/`nuts_calc_tex.py` は元々それぞれ独立に同一の桁数→範囲テーブルを `_init()` 内にネストした関数として持っていた(コード共有なしの2スクリプトのため)。issue #138 時点では `nuts_calc.py` 側だけがモジュールレベル関数に抽出済みだったため、本ファイルはそちらを import して再利用していた。issue #232 で `nuts_calc.py` を削除するにあたり、`nuts_calc_tex.py` 側のネスト関数も同じ理由でモジュールレベルへ昇格させ(`nuts_calc_tex.py:129-139`、[[nuts_calc_tex.py]] 参照)、本ファイルの import 先を `nuts_calc_tex.set_min_max_value()` へ切り替えた。挙動は変更していない(戻り値の型を `list[int]` から `tuple[int, int]` に揃えただけ、当時の `_resolve_ope_range()` の型注釈と整合させるため)。

### `-a/--a-value` の桁数解釈を `--a-digits`/`--b-digits` へ分離した理由(issue #230)

`_resolve_ope_range()`(旧名)は `params.get("a_value")` を桁数とみなして `nuts_calc_tex.set_min_max_value()` に渡す実装だった。この「`a_value` が文脈(command_type)によって桁数にも値そのものにもなる」という単一パラメータへの意味の二重化は `nuts_calc_tex.py` の `_init()` 側と全く同じ根本原因で、issue #174(B-5、`POST /generate-pdf` の内部プレゼンテーションAPI移行)配下の11個の移行issueがこの二重解釈を再現し損ねるリスクとして issue #230 が指摘した。issue #231(`nuts_calc.py`/`frontend/spa` というレガシー後方互換要求元の削除)を前提条件に解消したうえで、破壊的な書き換えとして対応した。

`_resolve_ope_range()` を public な `resolve_digit_count_range()` にリネームし、`value_key` 引数(`"a_value"`)を `digits_key` 引数(`"a_digits"`)に置き換えた(`problem_generation.py:201-217` 付近)。これにより `a_value`/`b_value` は `ope`/`lcm`/`gcd`/`divfrac` の各生成関数から一切読まれなくなり(既存の呼び出し元 `frontend/web/src/drillPresets.js` の `ope` プリセットは `a_digits`/`b_digits` へ移行済み)、`resolve_digit_count_range()` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に属する任意の将来の `_generate_*_pdf` 実装(`backend/app.py`)が呼ぶべき唯一の共有リゾルバとして docstring に明記した。「渡されたら拒否する」検証は追加していない(`a_value` が `ope` 等に渡されても単に無視されるだけ、`com` 等で `a_min`/`a_max` が既に無害に無視されているのと同じ既存の慣習)。

### `ope` 以外を明示的に `ValueError` で拒否している理由

`evenodd`/`multiples` 等、`ope` 以外の残り約19コマンド(issue #167 決定時点)は、それぞれ別の生成関数を使い、出力の型(fraction・真偽値・リスト等)も `ope` の a/b/operator/result 形とは異なる。1つのissue(#138)でこれら全てを実装すると、データ層のレスポンス形状(envelope)の設計判断を全コマンド分一度に確定させることになりスコープが過大になるため、issue #166 のsub-issue群(#167でアーキテクチャ決定、#168で `ope` 亜種、#169-#173で残りコマンド群)へ意図的に分割した(`frac`/`mixed` は #170、`compare` は #171 で実装済み、残り10コマンドは #172-#173 で対応予定)。未対応の呼び出しは黙って無視/変換せず、明示的なエラーメッセージで失敗させる。

### `ope` 亜種の相互排他バリデーション・term数レンジ解決を `nuts_calc_tex.py` から再現している理由(issue #168)

`POST /generate-problems` は argparse を経由しないため、`nuts_calc_tex.py` の `_init()` が担う「`--missing-value` は `--use-parentheses`/`--terms`系と併用不可」「`terms_min` <= `terms_max`」「`--use-parentheses` は term数フロアが3」等のバリデーション・デフォルト解決を、`_determine_ope_variant()` がリクエストパラメータに対して独自に再現する必要がある。ロジックを複製せず、フロア・上限のクランプ計算自体は `nuts_calc_tex.resolve_term_range()`(モジュールレベル関数、`TERM_COUNT_FLOOR_DEFAULT`/`TERM_COUNT_FLOOR_PARENTHESES`/`MAX_OPE_TERMS` を使用)をそのまま再利用している(`problem_generation.py:129`)。

### `frac`/`mixed` の CLI バリデーションを再現している理由(issue #170)

`ope` 亜種と同じ事情で、`frac`/`mixed` も argparse を経由しないため、`nuts_calc_tex.py` の `_init()` が担うバリデーション(`frac`: `same_denominator`×`different_denominators` 排他、`proper_operands` の digit 制約、`a/b_fraction_form` の operator/improper 制約。`mixed`: `decimal_places` 範囲、`terms` 系のクランプ、`reducible_mode` の operand-kind 制約)を `_generate_frac_problems`/`_generate_mixed_problems` が独自に再現する。両コマンドに共通する `numerator_digits`/`denominator_digits` 範囲チェックと `reducible_mode` の operator 制約チェックは、`_determine_ope_variant()` 同様ロジックを複製しないよう `_validate_fraction_digits()`/`_validate_reducible_operators()` として1箇所に集約し、`_generate_frac_problems`/`_generate_mixed_problems` の双方から呼び出している(`problem_generation.py:336-353`)。`mixed` の `_determine_mixed_terms()` は `terms`/`terms_min`/`terms_max`/`mixed_operators` から `terms_options_given` を判定し、`nuts_calc_tex.resolve_term_range()` を再利用する点も `_determine_ope_variant()` と同じパターンだが、`mixed` に `--use-parentheses` 相当のオプションは存在しないため `resolve_term_range()` の `use_parentheses` 引数は常に `False` を渡す。

### `compare` の kind 混在バリデーションを再現している理由(issue #171)

`nuts_calc_tex.py` の `_init()` は、`compare` の `--a-kind`/`--b-kind` が `['fraction']`(既定)以外のとき、`--comparison-pattern`(`same-denominator`/`same-numerator`)を明示的に拒否する(int の分母は常に1、decimal の分母は常に `10**decimal_places` のため、この2パターンは分数vs分数の場合しか意味を持たない)。この endpoint は argparse を経由しないため、`_generate_compare_problems` が同じ制約(`a_kind`/`b_kind` が既定 `['fraction']` から外れているのに `comparison_pattern` も非既定なら `ValueError`)をリクエストパラメータに対して再現する。`different-denominators`(既定パターン)のまま kind 混在する場合はエラーにしない — `nuts_calc_tex.generate_fraction_comparison_problems()` 自身が kind 混在時にパターンフィルタを内部でスキップするため(`nuts_calc_tex.py.md` の `compare` セクション参照)、int vs int のような組み合わせでも無限リトライにならない。

### `command_type` ディスパッチを if/elif から dict テーブルへ置き換えた理由(issue #169)

issue #167 の JSON contract 規約が事前に決定していた設計(下記「非-`ope` コマンド群向け JSON contract 規約」節の「`command_type` の許可判定」箇所)を issue #169 で初めて適用した。`_COMMAND_GENERATORS: dict[str, Callable]` に `command_type` 文字列と生成関数を1行ずつ追加するだけで新規コマンドを登録でき、共有の分岐チェーンを編集しないため、残り sub-issue(#172-#173)が並行作業してもコンフリクトしにくい。`ope` は当初 `_determine_ope_variant`/`renderer_name` 分岐を持つため `_generate_ope_problems()` として `generate_problems()` 内の早期分岐に置いていたが、issue #359 で共有 `generate()` 層へ分離する際、他コマンドと同じ `(params, count, start_index) -> list[<dataclass>]` シグネチャの `_generate_ope`(内部で `_determine_ope_variant` を呼び分ける)として `_COMMAND_GENERATORS["ope"]` に登録し、特別扱いを解消した。

### `100` を別 envelope で対応している理由(issue #169 → issue #228 で反転)

`nuts_calc_tex.generate_hundred_square()` は「`num` 個の問題」ではなく単一の `HundredSquareTable`(`left_values`/`top_values`、`answers` プロパティで加算表を計算)を返す。既存の `{"problems": [...]}` envelope は「`num` 個の同型 item のリスト」を前提としており、単一テーブルはこの意味論に合わない。

issue #169 の時点では、別 envelope 形状の新設は issue #167 相当のスコープを持つ契約決定であり本 issue 単体では重すぎると判断し、`_COMMAND_GENERATORS` に `100` を追加せず「not yet supported」`ValueError` にフォールスルーさせていた。2026-08-19 の issue #174 上の /mtg で、`POST /generate-pdf` の内部プレゼンテーション API 移行を `100` に進めるにあたり「どの command も JSON データ層契約をバイパスしてはならない」と決定し、issue #228 でこの対象外判断を反転した。

現在は専用関数 `generate_hundred_square_table()`(上記「動作の概要」参照)が、`problems` list とは兄弟関係の top-level `table` キーを持つ `{"table": {"left_values", "top_values", "answers"}}` を返す(`table` を `problems` の中にネストはしない)。`_COMMAND_GENERATORS`(list 契約)には引き続き `100` のエントリを持たせず、`generate_problems()` は `100` に対して、汎用の「not yet supported」ではなく `generate_hundred_square_table()` を名指しする targeted な `ValueError` を送出する(`100` はエンドポイントが手前で専用関数へルーティングするため、この分岐に到達するのは直接呼び出す caller/テストのみで、明示的なポインタが有用)。

### `ope` の reportlab 分岐を削除した理由(issue #232)

`nuts_calc.py`(ReportLab)は issue #232 で削除された。それ以前は素の2項 `ope` だけ `_generate_ope_problems_reportlab`/`_generate_ope_problems_latex` の二択があり、`--use-parentheses`/`--missing-value`/`--terms`系のいずれも `nuts_calc.py` に対応実装がなかったため、亜種フラグが判定された状態で `renderer_name == 'reportlab'` の場合は生成関数を呼ばずに `ValueError` を送出していた。`app.py` の `/generate-problems` ルートハンドラは既に `renderer_config.get_renderer_name()` を先に呼んでおり、`nuts_calc.py` 削除後は `latex` 以外の値がここに到達することは(直接呼び出す一部のテストを除き)ありえないため、この分岐自体とその根拠だったチェックはまるごと不要になった。`_generate_ope_problems()` は他の非-`ope` コマンド群と同じく、常に `_generate_ope_problems_latex` を呼ぶだけの実装になっている。

### `lcm`/`gcd` で生成関数を1つ共有している理由(issue #172)

`nuts_calc_tex.py` 自身が `lcm`/`gcd` の2コマンドを `generate_number_pair_problems(compute, nums_a, nums_b, order, start_index)` 1関数(`compute=math.lcm`/`math.gcd` で呼び分け、`nuts_calc_tex.py:3909-3925`)に集約しており、CLI側の `build_number_pair_pages(ini, compute, label)`(`nuts_calc_tex.py:3959-3969`)も同じパターンを踏襲している。`problem_generation.py` 側でも `_generate_com_problems`/`_generate_kuku_problems` のように2つの独立した関数を書くのではなく、共有ヘルパー `_generate_number_pair_problems(params, num, compute)` + `compute` だけを固定する薄いラッパー2つ(`_generate_lcm_problems`/`_generate_gcd_problems`)にした。これは issue #169 の「非-`ope` コマンド群向け JSON contract 規約」節が事前に想定していた設計(下記「`command_type` の許可判定」箇所)でもある。

### 共有バリデータ `validate_com_target()` を切り出した理由(issue #237)

issue #199 が `backend/app.py` に `_generate_com_pdf` を追加した際、既に本ファイルにあった `com` の `a_value` 検証(必須チェック + `MIN_COMPLEMENT_TARGET` 未満チェック)を再利用せず、同じロジック・同じエラーメッセージ文言をそのまま複製した。issue #230 の調査で、この重複が `#174`(B-5)の残り11個の移行issue(各々が新規 `_generate_*_pdf` を追加する)にも同じパターンで再発するリスクとして指摘され、issue #237 で解消した。`_generate_com_problems` 内にあった2チェックを公開関数 `validate_com_target(a_value: int | None) -> int`(`problem_generation.py:263-276` 付近)へ抽出し、`_generate_com_problems` と `app.py`(`app.py` は元々 `problem_generation` を import 済み)の `_generate_com_pdf` の双方がこれを呼ぶ。挙動・エラーメッセージは変更していない。今後 `_generate_*_pdf` を追加する際にリクエストパラメータのバリデーションが `problem_generation.py` に既存であれば、複製せずこのパターン(共有バリデータを抽出して両側から呼ぶ)に従う。issue #208 が `99` の `_generate_kuku_pdf` を追加した際、このパターンに従って `_generate_kuku_problems` 内の a_value 必須チェックを `validate_kuku_a_value(a_value: int | None) -> int`(`problem_generation.py:286-295`)へ抽出し、複製を避けた(`com` と異なり最小値チェックは持たない)。issue #209 が `_generate_squ_pdf` を追加する際、この規約に沿って最初から `_generate_squ_problems` 内の必須チェックを `validate_squ_start(a_value: int | None) -> int` へ抽出し、複製を経ずに両側から共有した(`com` と異なり `squ` には下限チェックがないため、切り出す内容は必須チェックのみ)。issue #210 の `_generate_pi_pdf` も同じ規約に従い、`validate_pi_start(a_value: int | None) -> int`(`problem_generation.py:311-320` 付近、`_generate_pi_problems` の直前)を最初から公開関数として `_generate_pi_problems` と `app.py` の `_generate_pi_pdf` の双方から呼ぶ形で実装した(`squ` と同様、下限チェックなし)。

### `divfrac` が `b_min < 1` を明示的に拒否している理由(issue #173)

`divfrac` は a÷b を未約分の a/b として出題するため、`b` が 0 だと表現不能な除算(0除算)になる。`nuts_calc_tex.py` の `_init()` は `args.command == 'divfrac' and args.b_min < 1` を明示的に拒否しており(`nuts_calc_tex.py:563-564`)、`_generate_divfrac_problems` も同じ制約をリクエストパラメータに対して再現する。`lcm`/`gcd`/`evenodd`/`multiples`/`divisors` にはこの制約がない(0除算のリスクがないため)。

### `dec2frac` が digit 系オプションを一切受け取らない理由(issue #173)

`generate_dec2frac_problems(order, start_index)` は `numerator_digits`/`denominator_digits` を引数に取らない — 小数の桁数(`decimal_places`)は `nuts_calc_tex.py` 側の固定定数 `DEC2FRAC_MIN_DECIMAL_PLACES`〜`MAX_DECIMAL_PLACES` からランダムに決まる設計であり、CLI 側にも対応するオプションがない。`_generate_dec2frac_problems` はこの既存シグネチャをそのまま反映しているだけで、独自の digit 検証を追加していない。

### `evenodd`/`multiples`/`divisors` が `a_digits` ショートハンドに対応しない理由(issue #172)

`nuts_calc_tex.py` の `_init()` は `--a-digits`/`--b-digits` → `set_min_max_value()` による桁数ショートハンド変換を `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS`(`'ope', '100', 'lcm', 'gcd', 'divfrac'`)のときのみ適用しており、`evenodd`/`multiples`/`divisors` はこの対象コマンドリストに含まれていない(CLIでは `--a-min`/`--a-max` を直接指定する)。エンドポイント側もこの挙動をそのまま再現し、3コマンドとも `resolve_digit_count_range()`(`a_digits` ショートハンド対応)ではなく `params.get("a_min", ...)`/`params.get("a_max", ...)` を直接読む。

- `com`/`99`/`aBc`/`squ`/`pi`/`frac`/`mixed`/`compare`/`evenodd`/`multiples`/`divisors`/`lcm`/`gcd`/`simplify`/`commondenom`/`frac2dec`/`dec2frac`/`divfrac` は `renderer_name` を一切参照しない(`_COMMAND_GENERATORS` の生成関数は `params`/`count`/`start_index` のみを受け取る)。`ope` を含む全コマンドが常に `nuts_calc_tex.py` の実装を使う(上記「非-`ope` コマンド群向け JSON contract 規約」節の「reportlab 分岐は持たない」箇所参照)。
- `100` は `POST /generate-problems` から `{"table": {...}}` envelope で取得できる(issue #228)。ただし `generate_problems()` を直接呼ぶと `100` は `ValueError`(`generate_hundred_square_table()` を案内)になる — エンドポイントが手前で専用関数へルーティングするため、この非対称は HTTP 経路には影響しない。`POST /generate-pdf` の `100` は issue #229 で内部プレゼンテーション API 経路へ移行し、`backend/three_layer_renderer.py` の `_generate_hundred_square_pdf` が `resolve_hundred_square_axes()` + `nuts_calc_tex.generate_hundred_square()` をプロセス内で呼ぶ(subprocess は経由しない。`renderers.run` は issue #297 で削除)。CLI(`nuts_calc_tex.py 100 ...`)は従来どおり `build_hundred_square_pages` 経路。
- `compare` の `a_kind`/`b_kind`(既定 `['fraction']`)は `mixed` の `MIXED_OPERAND_KINDS` 既定(3種類全て)と異なる。issue #171 以前の分数vs分数のみの挙動を後方互換のまま保つための意図的な非対称で、明示的に `a_kind`/`b_kind` を指定しない限り既存の呼び出し元(両フロントエンドとも現状未使用)の挙動は変わらない。
