# `backend/app.py`

## 目的・役割

`nuts_calc_tex.py`(issue #232 以前は `nuts_calc.py` も)を Web 経由で呼び出すための薄い Flask API。エンドポイントは `POST /generate-pdf`(PDF 生成)、`POST /generate-problems`(問題データのみ生成、PDF非生成、issue #138)、`GET /renderer-info`(現在有効なレンダラー名の取得、issue #46)の3つ。コマンド構築・レンダラー選択・subprocess 実行のロジックは `backend/renderers.py`([[renderers.py]] 参照、issue #36)に、問題データのみのプロセス内直接生成ロジックは `backend/problem_generation.py`([[problem_generation.py]] 参照、issue #138)に切り出されており、本ファイルは JSON パース・`renderers`/`problem_generation` 呼び出し・HTTP レスポンス変換のみを担う。`POST /generate-pdf` は issue #199 の `com` に続き、issue #205(#201 パターン1a移行トラッキングissueの最初の子issue)で plain 2-term `ope`(横式 add/sub/mul/div/mix、`--vertical`/`--intermediate`/`--use-parentheses`/`--missing-value`/`terms`系/`--mixed-operators` いずれも未指定のケース)も内部プレゼンテーション API 経路に移行した。

## 動作の概要

- `POST /generate-pdf`: 必須パラメータ(`paper_size`/`command_type`)のみ本ファイルで検証する(`app.py:196-197` 付近)。`command_type == 'com'` の場合(issue #199、#174(B-5) の最初のコマンドグループ移行)は `_generate_com_pdf(data, PDF_OUTPUT_DIR)` を、plain 2-term `ope` リクエスト(`_is_plain_ope_pdf_request(data)` が真、issue #205、#201 パターン1a移行トラッキングissueの最初の子issue)の場合は `_generate_ope_pdf(data, PDF_OUTPUT_DIR)` を呼び、いずれも `nuts_calc_tex.py` の内部プレゼンテーション API(`build_presentation_document_tex`、issue #183)を in-process で使って PDF を生成する。それ以外の全 `command_type`/`ope` のバリアントは従来どおり `renderers.get_renderer_name()` でレンダラーを解決し、`renderers.run(data, PDF_OUTPUT_DIR, renderer_name)` を呼ぶ subprocess 経路のまま。`data`(リクエスト JSON)はそのまま `renderers.run` に渡され、CLI 引数への変換は `renderers.build_command` が担う。成功時は生成された PDF をそのまま `send_file` で返す。失敗時は例外の型に応じて `{'error': ...}` を HTTP 500 で返す: `ValueError`(レンダラー名不正・必須パラメータ欠如・`_generate_com_pdf`/`_generate_ope_pdf` のバリデーションエラー・LaTeX バイナリ未検出)、`subprocess.CalledProcessError`(subprocess レンダラー実行失敗)、`RuntimeError`(`_generate_com_pdf`/`_generate_ope_pdf` 内で `engine_adapter.compile()` のコンパイル失敗を変換したもの、後述)、`FileNotFoundError`(スクリプト未検出)、その他 `Exception`。
  - `_generate_com_pdf(data, output_dir)`(`app.py:22-86`、issue #199): `com` 専用のベーシックケースのみ対応する PDF ビルダー。`a_value` の検証(必須、`nuts_calc_tex.MIN_COMPLEMENT_TARGET` 以上)は `problem_generation.validate_com_target(data.get('a_value'))` へ委譲する(issue #237 以前は本関数がインラインで重複実装していたが、`backend/problem_generation.py`([[problem_generation.py]] 参照)の `_generate_com_problems` と共有する形に統一した)。`rows`/`columns`(既定 `nuts_calc_tex.DEFAULT_ROWS`=10/2、CLI 既定と一致)を検証したうえで、`nuts_calc_tex.generate_com_problems` → `PresentationPage` → `build_presentation_document_tex(content_format=build_com_slot_content_tex, page_shell=DEFAULT_PAGE_SHELL, content_area_layout=ContentAreaLayout(rows, columns), show_answer=False)` の順に呼び、`nuts_calc_tex.get_latex_engine_adapter()` で解決したエンジンの `compile()` を直接呼んで PDF ファイルを書き出す。常に1ページ・blank(練習用)版のみを返す — `with_bottom_answer`/`with_name_field`/複数ページ/`merge` は未対応(issue #199 のスコープ外、issue 本文に明記)。
  - `_generate_com_pdf` は `data.get('a_value')` を補数ターゲット(値そのもの)として直接読む。`com` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれないため、これは issue #230 の再設計後も無変更で正しい。
  - `_is_plain_ope_pdf_request(data)`(`app.py:89-111`、issue #205): ルーティング判定専用の述語。`command_type == 'ope'` かつ `vertical`/`intermediate`(それぞれ別コンテンツフォーマットのパターン6/5)、`use_parentheses`/`missing_value`(未移行のパターン2/tree variant)、`terms`/`terms_min`/`terms_max`/`mixed_operators`(未移行のmulti-term variant、#207)のいずれも指定されていない場合のみ真を返す。真の場合だけ `_generate_ope_pdf` へルーティングし、それ以外(variant フラグが1つでも立っている場合)は他の `command_type` と同じ subprocess 経路にフォールバックする。
  - `_generate_ope_pdf(data, output_dir)`(`app.py:114-192`、issue #205): plain 2-term `ope` 専用の PDF ビルダー。`_generate_com_pdf` と同じ構造だが、`ope` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれるため `a`/`b` の範囲は `problem_generation.resolve_digit_count_range(data, 'a_digits', 'a_min', 'a_max', ...)`(`b` も同様)経由で解決する(`_generate_com_pdf` の docstring がこの区別を明記していた設計判断どおり)。`operator`(既定 `problem_generation.DEFAULT_OPERATOR` = `['add']`)・`a_decimal_places`/`b_decimal_places`・`carry_mode`/`remainder_mode`/`result_max` をそのまま `nuts_calc_tex.generate_ope_problems` へ渡し、`content_format=nuts_calc_tex.build_ope_slot_content_tex`(#184 のパターンを踏襲した番号なし Layer-3 content、`nuts_calc_tex.py` 側で新設)を使って `build_presentation_document_tex` を呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約は `_generate_com_pdf` と同一。
  - issue #174(B-5)の残る移行issue(`100`/`lcm`/`gcd`/`divfrac` 系、`ope` の tree/multi-term variant)が将来追加する同種の `_generate_*_pdf` 実装も、`DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれるコマンドでは `_generate_ope_pdf` と同じく `problem_generation.resolve_digit_count_range` を呼ぶ必要がある。
  - `engine_adapter.compile()` はコンパイル失敗時に例外を raise せず `nuts_calc_tex.failure()`(`print()` + `exit(1)` = `SystemExit`)を呼ぶ設計で、これは元々 CLI の subprocess 隔離を前提にしている(`LatexEngineAdapter.compile` の docstring 参照)。`_generate_com_pdf`/`_generate_ope_pdf` を Flask プロセス内で直接呼ぶこの経路ではその前提が崩れるため、`compile()` 呼び出しをそれぞれ `contextlib.redirect_stdout` で囲んで `failure()` の出力を捕捉し、`SystemExit` を `RuntimeError(f'PDF generation failed: {captured}')` に変換して呼び出し元(`generate_pdf` ルート)まで伝播させる。ルート側の `except RuntimeError` 節でこれを 500 に変換する。未対応のまま放置すると、リクエストスレッドが JSON レスポンスを返さずに異常終了するリスクがあった。
- `POST /generate-problems`(issue #138): 必須パラメータ(`paper_size`/`command_type`/`num`、`num` は正の整数)を本ファイルで検証する(`app.py`の`generate_problems`ハンドラ)。`renderers.get_renderer_name()` でレンダラーを解決し、`problem_generation.generate_problems(data, renderer_name)` を呼ぶ。成功時は `{'problems': [...]}` をそのまま JSON で返す(PDFファイルは生成しない)。`command_type='ope'` 以外や `ope` の一部亜種フラグなど未対応の入力は `problem_generation` 側が送出する `ValueError` を捕捉し `{'error': ...}` を HTTP 500 で返す(`/generate-pdf` と同じ「必須パラメータ欠如は400、ロジック層のエラーは500」という区分けを踏襲)。
- `GET /renderer-info`(issue #46): `renderers.get_renderer_name()` の結果をそのまま `{'renderer': 'latex'}` として返す(issue #186 以降、`latex` がデフォルトかつ唯一到達可能なレンダラーのため、通常は常に `'latex'`)。`nuts_calc.py` が `--vertical`(筆算)を持たなくなった(issue #46)ため、フロントエンドがリクエスト前にどちらのレンダラーが有効かを判定し、`latex` の場合のみ筆算 UI を出す目的で追加された(`frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js` が呼ぶ。かつては `frontend/spa/src/GradeDrills.jsx`/`CustomGenerator.jsx` も呼んでいたが、`frontend/spa` 自体が issue #233 で削除された)。env 変数が不正な場合は `renderers.get_renderer_name()` が送出する `ValueError` を捕捉し、`{'error': ...}` を HTTP 500 で返す。

## 統合ポイント

- 呼び出し元: `frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js`(`GET /renderer-info`)、`frontend/web/src/presetDetail.js`(`POST /generate-problems`、issue #139。`command_type: 'ope'` かつ未対応フラグなしのプリセットのみ、マウント時・設定変更時にデバウンスして呼び出す)。`frontend/web` には `com` を使うプリセットも自由入力フォームも存在せず(`command_type_com` という翻訳文字列だけが `frontend/web/src/strings.ja.json` に孤立して残っている)、`frontend/web` からは `command_type: 'com'` の `POST /generate-pdf` に到達不可。かつては `frontend/spa/src/CustomGenerator.jsx`(`frontend/spa/src/drillPresets.js` の「10のあわせて」`a_value: 10`/「100のあわせて」`a_value: 100` プリセットと、自由入力フォームの `<option value="com">` から到達)が `command_type: 'com'` を選択できる唯一のフロントエンドだったが、`frontend/spa` 自体が issue #233 で削除されたため、現状 `command_type: 'com'` の `POST /generate-pdf` へ到達できる UI 経路は存在しない(直接 API を叩けば依然到達可能)。同様に `frontend/spa/src/GradeDrills.jsx` が呼んでいた `GET /renderer-info` の呼び出しも、`frontend/web` 側の上記3ファイルに引き継がれている。
- 呼び出し先: `command_type == 'com'` の場合は `backend/nuts_calc_tex.py` の内部プレゼンテーション API(`generate_com_problems`/`build_com_slot_content_tex`/`PresentationPage`/`ContentAreaLayout`/`DEFAULT_PAGE_SHELL`/`build_presentation_document_tex`/`get_latex_engine_adapter`、issue #199)を直接呼ぶほか、`backend/problem_generation.py`(`validate_com_target`、issue #237)を `a_value` 検証に呼ぶ。plain 2-term `ope` リクエスト(`_is_plain_ope_pdf_request` が真)の場合は同じ内部プレゼンテーション API を `generate_ope_problems`/`build_ope_slot_content_tex`(issue #205)で呼ぶほか、`backend/problem_generation.py` の `resolve_digit_count_range`/`DEFAULT_A_MIN`/`DEFAULT_A_MAX`/`DEFAULT_B_MIN`/`DEFAULT_B_MAX`/`DEFAULT_OPERATOR` を `a`/`b` レンジ・演算子の既定値解決に呼ぶ。それ以外は従来どおり `backend/renderers.py`(レンダラー選択・PDF生成実行の subprocess 経路)、`backend/problem_generation.py`(問題データのみのプロセス内直接生成)。

## 注意事項・既知の制限

- `nuts_calc_tex.py` 側のバリデーション失敗メッセージは `print()`(stdout)に出力されるため、`subprocess.CalledProcessError` ハンドラは `e.stdout` を優先し(空なら `e.stderr` にフォールバック)、それを `error` フィールドに含める(issue #37 で修正)。`nuts_calc.py`(issue #232 で削除)側でも `com`/`99`/`squ`/`pi`/`100` のバリデーション失敗が引数なし `exit()`(終了コード0、`subprocess.run(check=True)` が例外を送出しない)になっていた不具合を同 issue #37 で `exit(1)` に修正済みだった。修正前はこの経路で `CalledProcessError` すら発生せず、後続の `send_file` が `FileNotFoundError` になり実際の理由と無関係な「Renderer script not found」を返していた。
- backend の URL がフロントエンド側にハードコードされている(`frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js`・`presetDetail.js` それぞれの `API_BASE = 'http://127.0.0.1:5000'` の既知の制約。かつて併存していた `frontend/spa/src/CustomGenerator.jsx`/`GradeDrills.jsx` も同様の制約を持っていたが、`frontend/spa` 自体が issue #233 で削除された)。
- レンダラー選択は env 変数のみで、リクエストごとの指定はできない(issue #36 のスコープ)。`GET /renderer-info` はこの env 変数由来のレンダラー名をフロントエンドに公開する読み取り専用エンドポイントであり、フロントエンドからレンダラーを切り替える手段ではない。
- `command_type == 'com'`、および plain 2-term `ope` リクエストは、`nuts_calc_tex.get_latex_engine_adapter()` を `_generate_com_pdf`/`_generate_ope_pdf` から直接呼ぶため、`NUTS_CALC_TEX_ENGINE` 環境変数が不正な場合の失敗経路が他コマンドと異なる: 他コマンド(subprocess 経路)ではこの `ValueError` は CLI 側の `main()` 内で `failure()`(`exit(1)`)に変換され `CalledProcessError` として 500 になるが、これらの内部API経路では素の `ValueError` がそのまま 500 になる(いずれも HTTP 500 自体は同じだが `error` フィールドの文言が異なる)。環境設定ミス由来でリクエストごとに変動しないため許容している既知の差異(issue #199)。
- `com`、および plain 2-term `ope` は常に1ページ・blank(練習用)版のみを返す。`with_bottom_answer`/`with_name_field`/複数ページ(`page` > 1)/`merge` はそれぞれ `_generate_com_pdf`/`_generate_ope_pdf` に配線しておらず、リクエストに含めても無視される(issue #199/#205 のスコープ外。`#174`(B-5)の以降のコマンドグループ移行、またはそれぞれの追加スコープ issue で対応)。
- plain 2-term `ope` の判定(`_is_plain_ope_pdf_request`)は `vertical`/`intermediate`/`use_parentheses`/`missing_value`/`terms`/`terms_min`/`terms_max`/`mixed_operators` のいずれかが指定されていれば内部API経路を使わず subprocess 経路にフォールバックする。これらのバリアントは `docs/latex/tex_content_format_taxonomy.md` 上で別のコンテンツフォーマットパターン(5/6)か、パターン1a内の未移行variant(tree/multi-term、issue #206/#207)であり、`_generate_ope_pdf` はそれらを一切サポートしない。
