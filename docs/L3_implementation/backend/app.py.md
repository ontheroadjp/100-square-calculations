# `backend/app.py`

## 目的・役割

`nuts_calc_tex.py` を Web 経由で呼び出す Flask API。エンドポイントは `POST /generate-pdf`、`POST /generate-problems`(issue #138)、`GET /renderer-info`(issue #46)の3つ。JSON/HTTP 境界を本ファイルが担い、未移行 PDF コマンドの CLI/subprocess 実行は `backend/renderers.py`、問題データのみのプロセス内生成は `backend/problem_generation.py` に委譲する。`POST /generate-pdf` の内部プレゼンテーション API 経路は `com`(#199)、`ope` の plain/tree/flat multi-term(#205〜#207)、`99`(#208)、`squ`(#209)、`pi`(#210)、`lcm`(#211)、`gcd`(#212)へ段階的に展開済みである。

## 動作の概要

`command_type == 'gcd'` は `_generate_gcd_pdf` を呼び、内部プレゼンテーション API で生成するため subprocess fallback の対象ではない(`app.py:166-229,770-805`)。

- `POST /generate-pdf`(`app.py:770-827`): `paper_size`/`command_type` を検証し、`com`/`lcm`/`gcd`/`99`/`pi`/移行済み `ope` variants/`squ` は対応する `_generate_*_pdf` で内部プレゼンテーション API を呼ぶ。それ以外は `renderers.run(data, PDF_OUTPUT_DIR, renderer_name)` の subprocess 経路へフォールバックする。成功時は `send_file` で PDF を返し、入力・コンパイル・subprocess・ファイルの各例外は既存の JSON 500 応答へ変換する。
  - `_generate_com_pdf(data, output_dir)`(`app.py:22-86`、issue #199): `com` 専用のベーシックケースのみ対応する PDF ビルダー。`a_value` の検証(必須、`nuts_calc_tex.MIN_COMPLEMENT_TARGET` 以上)は `problem_generation.validate_com_target(data.get('a_value'))` へ委譲する(issue #237 以前は本関数がインラインで重複実装していたが、`backend/problem_generation.py`([[problem_generation.py]] 参照)の `_generate_com_problems` と共有する形に統一した)。`rows`/`columns`(既定 `nuts_calc_tex.DEFAULT_ROWS`=10/2、CLI 既定と一致)を検証したうえで、`nuts_calc_tex.generate_com_problems` → `PresentationPage` → `build_presentation_document_tex(content_format=build_com_slot_content_tex, page_shell=DEFAULT_PAGE_SHELL, content_area_layout=ContentAreaLayout(rows, columns), show_answer=False)` の順に呼び、`nuts_calc_tex.get_latex_engine_adapter()` で解決したエンジンの `compile()` を直接呼んで PDF ファイルを書き出す。常に1ページ・blank(練習用)版のみを返す — `with_bottom_answer`/`with_name_field`/複数ページ/`merge` は未対応(issue #199 のスコープ外、issue 本文に明記)。
  - `_generate_com_pdf` は `data.get('a_value')` を補数ターゲット(値そのもの)として直接読む。`com` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれないため、これは issue #230 の再設計後も無変更で正しい。
  - `_generate_lcm_pdf(data, output_dir)`(issue #211): `lcm` 専用のベーシックケースのみ対応する PDF ビルダー。`_generate_com_pdf` と同じ構造だが、`lcm` は `ope`/`100`/`gcd`/`divfrac` と同じく `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれるため `a`/`b` の範囲は `_generate_ope_pdf` と同じく `problem_generation.resolve_digit_count_range(data, 'a_digits', 'a_min', 'a_max', ...)`(`b` も同様)経由で解決する。ルーティング判定用の `_is_lcm_pdf_request` ヘルパーは存在しない — `lcm` は `vertical`/`intermediate`/`use_parentheses`/`missing_value`/`terms`系などの variant フラグを一切持たない(`nuts_calc_tex.py` の `_init()` が `command != 'ope'` を理由に無条件で拒否)ため、`generate_pdf()` 内で `com` と同じ単純な `command_type == 'lcm'` の等価判定だけでルーティングできる。`nuts_calc_tex.generate_number_pair_problems(math.lcm, nums_a, nums_b, rows * columns, 1)` → `PresentationPage` → `build_presentation_document_tex(content_format=nuts_calc_tex.build_lcm_slot_content_tex)` の順に呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約は `_generate_com_pdf`/`_generate_ope_pdf` と同一。
  - `_generate_gcd_pdf(data, output_dir)`(`app.py:166-229`、issue #212): `_generate_lcm_pdf` と同じ桁数レンジ解決・レイアウト検証・1ページ blank 版という基本ケース限定の構造を使い、生成関数だけを `generate_number_pair_problems(math.gcd, ...)`、Layer-3 content だけを `build_gcd_slot_content_tex` に差し替える。`command_type == 'gcd'` の完全一致でのみこの経路へ入り、CLI と他コマンドの subprocess fallback は変更しない。
  - `_generate_kuku_pdf(data, output_dir)`(issue #208): `99`(九九)専用の PDF ビルダー。`_generate_com_pdf` と同じ構造で、`a_value` の検証(必須)は `problem_generation.validate_kuku_a_value(data.get('a_value'))` へ委譲する(`validate_com_target` の抽出パターンをそのまま踏襲)。`_generate_com_pdf` と異なり `descend`/`shuffle` も `data` から読んで `nuts_calc_tex.generate_kuku_problems(a_value, rows*columns, 1, descend, shuffle)` へそのまま渡す — `com` の他の未対応フラグと違い、`frontend/web` の `g2-kuku` プリセット(出題順序設定)が実際にこれらを送信する生きた経路があるため、無視すると回帰になる。`rows`/`columns` の既定・検証は `_generate_com_pdf` と同一。`content_format=nuts_calc_tex.build_kuku_slot_content_tex` を使う(常に非-reverse の `$a \times b = c$` 形。`reverse` は未対応)。`with_bottom_answer`/`with_name_field`/複数ページ/`merge` は `_generate_com_pdf` と同様に未対応。
  - `_generate_pi_pdf(data, output_dir)`(issue #210): `pi` 専用のベーシックケースのみ対応する PDF ビルダー。`_generate_com_pdf` と同じ構造で、`a_value`(起点となる整数)を `problem_generation.validate_pi_start(data.get('a_value'))` へ委譲して検証する(`com` の `validate_com_target` と対になる共有バリデータ、issue #237 の規約に従い最初から `problem_generation.py` 側に抽出)。`pi` は `com` と同じく `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれないため `a_value` を直接読む。`descend`/`shuffle` は `bool(data.get(..., False))` で読み、`nuts_calc_tex.generate_pi_problems(start_num, rows*columns, 1, descend, shuffle)` → `PresentationPage` → `build_presentation_document_tex(content_format=nuts_calc_tex.build_pi_slot_content_tex)` の順に呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約、`reverse`(式の左右反転)/`with_bottom_answer`/`with_name_field`/複数ページ/`merge` が未対応な点は `_generate_com_pdf` と同一(issue #210 のスコープ外)。
  - `_is_plain_ope_pdf_request(data)`(issue #205): ルーティング判定専用の述語。`command_type == 'ope'` かつ `vertical`/`intermediate`(それぞれ別コンテンツフォーマットのパターン6/5)、`use_parentheses`/`missing_value`(パターン2/tree variant。`use_parentheses` は issue #206 で `_is_tree_ope_pdf_request` に切り出して別途移行済み)、`terms`/`terms_min`/`terms_max`/`mixed_operators`(flat multi-term variant。issue #207 で `_is_multi_term_ope_pdf_request` に切り出して別途移行済み)のいずれも指定されていない場合のみ真を返す。真の場合だけ `_generate_ope_pdf` へルーティングし、それ以外(variant フラグが1つでも立っている場合)は他の `command_type` と同じ subprocess 経路にフォールバックする。
  - `_generate_ope_pdf(data, output_dir)`(issue #205): plain 2-term `ope` 専用の PDF ビルダー。`_generate_com_pdf` と同じ構造だが、`ope` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれるため `a`/`b` の範囲は `problem_generation.resolve_digit_count_range(data, 'a_digits', 'a_min', 'a_max', ...)`(`b` も同様)経由で解決する(`_generate_com_pdf` の docstring がこの区別を明記していた設計判断どおり)。`operator`(既定 `problem_generation.DEFAULT_OPERATOR` = `['add']`)・`a_decimal_places`/`b_decimal_places`・`carry_mode`/`remainder_mode`/`result_max` をそのまま `nuts_calc_tex.generate_ope_problems` へ渡し、`content_format=nuts_calc_tex.build_ope_slot_content_tex`(#184 のパターンを踏襲した番号なし Layer-3 content、`nuts_calc_tex.py` 側で新設)を使って `build_presentation_document_tex` を呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約は `_generate_com_pdf` と同一。
  - `_is_tree_ope_pdf_request(data)`(issue #206): ルーティング判定専用の述語。`command_type == 'ope'` かつ `use_parentheses` が真で、かつ `vertical`/`intermediate`/`missing_value` のいずれも指定されていない場合のみ真を返す(いずれも `nuts_calc_tex.py` の `_init()` バリデーションで `--use-parentheses` と併用不可、`nuts_calc_tex.py:676-692`)。`terms`/`terms_min`/`terms_max`/`mixed_operators` は `--use-parentheses` 自身の N項一般化(issue #71)であり、`_is_plain_ope_pdf_request` とは異なりこれらが指定されていても真を返す(tree variant として内部 API へルーティングする)。
  - `_generate_tree_ope_pdf(data, output_dir)`(issue #206): `ope --use-parentheses`(tree variant)専用の PDF ビルダー。`a`/`b` レンジは `_generate_ope_pdf` と同じく `problem_generation.resolve_digit_count_range` 経由で解決する。`terms`/`terms_min`/`terms_max` は `problem_generation._determine_ope_variant` の tree 分岐と同じロジック(`terms` が指定されていれば `terms_min`/`terms_max` を上書き、`nuts_calc_tex.resolve_term_range(..., use_parentheses=True)` でフロア(`TERM_COUNT_FLOOR_PARENTHESES`=3)にクランプ)をこの関数内で再実装している(`_determine_ope_variant` 自体は missing_value/multi_term 分岐も持つため直接は呼ばない)。`nuts_calc_tex.generate_tree_ope_problems` → `PresentationPage` → `build_presentation_document_tex(content_format=nuts_calc_tex.build_tree_ope_slot_content_tex)` の順に呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約は `_generate_com_pdf`/`_generate_ope_pdf` と同一。
  - `_is_multi_term_ope_pdf_request(data)`(issue #207): ルーティング判定専用の述語。`command_type == 'ope'` かつ `vertical`/`intermediate`/`use_parentheses`/`missing_value` のいずれも指定されておらず、かつ `mixed_operators` が真、または `terms`/`terms_min`/`terms_max` のいずれかが指定されている場合のみ真を返す。`nuts_calc_tex.py` の `_ope_uses_multi_term(ini)` 述語(`nuts_calc_tex.py:3091-3097`)と同じ条件をルーティング層で先取りしている。
  - `_generate_multi_term_ope_pdf(data, output_dir)`(issue #207): かっこなし flat multi-term `ope` 専用の PDF ビルダー。`a`/`b` レンジは `_generate_ope_pdf`/`_generate_tree_ope_pdf` と同じく `problem_generation.resolve_digit_count_range` 経由で解決する。`terms`/`terms_min`/`terms_max` の解決は `_generate_tree_ope_pdf` と同型だが、`nuts_calc_tex.resolve_term_range(..., use_parentheses=False)` を呼ぶ点が異なる(フロアは `TERM_COUNT_FLOOR_DEFAULT`=2)。`nuts_calc_tex.generate_multi_term_ope_problems` → `PresentationPage` → `build_presentation_document_tex(content_format=nuts_calc_tex.build_multi_term_ope_slot_content_tex)` の順に呼ぶ。`rows`/`columns` の既定・検証・常に1ページ・blank 版のみという制約は他の `_generate_*_pdf` と同一。これで #201(パターン1a移行トラッキングissue)の `ope` バリアント(plain 2-term/tree/multi-term)が全て内部プレゼンテーション API 経路に移行した。
  - `_generate_squ_pdf(data, output_dir)`(issue #209): `squ` 専用のベーシックケースのみ対応する PDF ビルダー。`_generate_com_pdf` と同じ構造・同じスコープ制約(常に1ページ・blank 版のみ、`descend`/`shuffle`/`reverse`/`with_bottom_answer`/`with_name_field`/複数ページ/`merge` は未対応)。`a_value` の検証(必須のみ、`com` と異なり下限チェックなし)は `problem_generation.validate_squ_start(data.get('a_value'))` へ委譲する(`validate_com_target`/issue #237 のデデュープパターンを踏襲)。`squ` は `nuts_calc_tex.DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれないため `a_value` を開始する二乗数の起点として直接読む(`com` と同じ理由)。`nuts_calc_tex.generate_squ_problems(start_num, rows*columns, 1, False, False)`(`descend`/`shuffle` は常に `False`)→ `PresentationPage` → `build_presentation_document_tex(content_format=build_squ_slot_content_tex, ...)` の順に呼ぶ。
  - 将来 `divfrac` など `DIGIT_COUNT_SHORTHAND_COMMANDS` に含まれる残りのコマンドを移行する場合も、`_generate_lcm_pdf`/`_generate_gcd_pdf` と同じく `problem_generation.resolve_digit_count_range` を呼ぶ必要がある。
  - `engine_adapter.compile()` はコンパイル失敗時に例外を raise せず `nuts_calc_tex.failure()`(`print()` + `exit(1)` = `SystemExit`)を呼ぶ設計で、これは元々 CLI の subprocess 隔離を前提にしている(`LatexEngineAdapter.compile` の docstring 参照)。`_generate_com_pdf`/`_generate_lcm_pdf`/`_generate_gcd_pdf`/`_generate_kuku_pdf`/`_generate_pi_pdf`/`_generate_ope_pdf`/`_generate_tree_ope_pdf`/`_generate_multi_term_ope_pdf`/`_generate_squ_pdf` を Flask プロセス内で直接呼ぶこの経路ではその前提が崩れるため、`compile()` 呼び出しをそれぞれ `contextlib.redirect_stdout` で囲んで `failure()` の出力を捕捉し、`SystemExit` を `RuntimeError(f'PDF generation failed: {captured}')` に変換して呼び出し元(`generate_pdf` ルート)まで伝播させる。ルート側の `except RuntimeError` 節でこれを 500 に変換する。未対応のまま放置すると、リクエストスレッドが JSON レスポンスを返さずに異常終了するリスクがあった。
- `POST /generate-problems`(issue #138): 必須パラメータ(`paper_size`/`command_type`/`num`、`num` は正の整数)を本ファイルで検証する(`app.py`の`generate_problems`ハンドラ)。`renderers.get_renderer_name()` でレンダラーを解決し、`problem_generation.generate_problems(data, renderer_name)` を呼ぶ。成功時は `{'problems': [...]}` をそのまま JSON で返す(PDFファイルは生成しない)。`command_type='ope'` 以外や `ope` の一部亜種フラグなど未対応の入力は `problem_generation` 側が送出する `ValueError` を捕捉し `{'error': ...}` を HTTP 500 で返す(`/generate-pdf` と同じ「必須パラメータ欠如は400、ロジック層のエラーは500」という区分けを踏襲)。
- `GET /renderer-info`(issue #46): `renderers.get_renderer_name()` の結果をそのまま `{'renderer': 'latex'}` として返す(issue #186 以降、`latex` がデフォルトかつ唯一到達可能なレンダラーのため、通常は常に `'latex'`)。`nuts_calc.py` が `--vertical`(筆算)を持たなくなった(issue #46)ため、フロントエンドがリクエスト前にどちらのレンダラーが有効かを判定し、`latex` の場合のみ筆算 UI を出す目的で追加された(`frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js` が呼ぶ。かつては `frontend/spa/src/GradeDrills.jsx`/`CustomGenerator.jsx` も呼んでいたが、`frontend/spa` 自体が issue #233 で削除された)。env 変数が不正な場合は `renderers.get_renderer_name()` が送出する `ValueError` を捕捉し、`{'error': ...}` を HTTP 500 で返す。

## 統合ポイント

- `frontend/web/src/drillPresets.js` の `g5-gcd` は `command_type: 'gcd'` と `a_min`/`a_max`/`b_min`/`b_max` を送るため、issue #212 の内部 API 経路へ実際に到達する。
- `command_type == 'gcd'` は標準ライブラリ `math.gcd`、`nuts_calc_tex.generate_number_pair_problems`、`build_gcd_slot_content_tex`、および `problem_generation.resolve_digit_count_range` を呼ぶ(`app.py:166-229`)。
- 呼び出し元: `frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js`(`GET /renderer-info`)、`frontend/web/src/presetDetail.js`(`POST /generate-problems`、issue #139。`command_type: 'ope'` かつ未対応フラグなしのプリセットのみ、マウント時・設定変更時にデバウンスして呼び出す)。`frontend/web` には `com`/`pi` を使うプリセットも自由入力フォームも存在せず(`command_type_com`/`command_type_pi` という翻訳文字列だけが `frontend/web/src/strings.ja.json` に孤立して残っている)、`frontend/web` からは `command_type: 'com'`/`'pi'` いずれの `POST /generate-pdf` にも到達不可(issue #210 実装時に `frontend/web/src/drillPresets.js`/`drillCatalog.js` を確認して判明)。かつては `frontend/spa/src/CustomGenerator.jsx`(`frontend/spa/src/drillPresets.js` の「10のあわせて」`a_value: 10`/「100のあわせて」`a_value: 100` プリセットと、自由入力フォームの `<option value="com">` から到達)が `command_type: 'com'` を選択できる唯一のフロントエンドだったが、`frontend/spa` 自体が issue #233 で削除されたため、現状 `command_type: 'com'`/`'pi'` の `POST /generate-pdf` へ到達できる UI 経路は存在しない(直接 API を叩けば依然到達可能)。同様に `frontend/spa/src/GradeDrills.jsx` が呼んでいた `GET /renderer-info` の呼び出しも、`frontend/web` 側の上記3ファイルに引き継がれている。`command_type: '99'` は `com`/`pi` と異なり `frontend/web` から実際に到達可能: `drillPresets.js` の `g2-kuku` プリセット(「2年生」→「かけ算」→「九九」)が `dan`(段、`'1'`〜`'9'`)選択時に `command_type: '99'` の `POST /generate-pdf` を送信し、「出題順序」設定に応じて `descend`/`shuffle` も付与する(`dan === 'mixed'` の場合は `command_type: 'ope'` にフォールバックする別経路)。`command_type: 'squ'` は `frontend/web` の「平方数の計算」プリセット(`drillPresets.js` の `ungraded-squ`)から到達可能で、`command_type`/`a_value` のみを送信する(設定項目なし)。`command_type: 'lcm'` も `frontend/web` から到達可能: `drillPresets.js` の学年5「公倍数・最小公倍数」プリセット(`g5-lcm`)が `command_type: 'lcm'`/`a_min`/`a_max`/`b_min`/`b_max` を送信する(設定項目なし、`squ` と同型)。
- 呼び出し先: `command_type == 'com'` の場合は `backend/nuts_calc_tex.py` の内部プレゼンテーション API(`generate_com_problems`/`build_com_slot_content_tex`/`PresentationPage`/`ContentAreaLayout`/`DEFAULT_PAGE_SHELL`/`build_presentation_document_tex`/`get_latex_engine_adapter`、issue #199)を直接呼ぶほか、`backend/problem_generation.py`(`validate_com_target`、issue #237)を `a_value` 検証に呼ぶ。`command_type == 'lcm'` の場合(issue #211)は同じ内部プレゼンテーション API を標準ライブラリ `math.lcm` と `nuts_calc_tex.generate_number_pair_problems`/`build_lcm_slot_content_tex` で呼ぶほか、`problem_generation.resolve_digit_count_range`/`DEFAULT_A_MIN`/`DEFAULT_A_MAX`/`DEFAULT_B_MIN`/`DEFAULT_B_MAX` を `a`/`b` レンジの既定値解決に呼ぶ。`command_type == '99'` の場合は同じ内部プレゼンテーション API を `generate_kuku_problems`/`build_kuku_slot_content_tex`(issue #208)で呼ぶほか、`backend/problem_generation.py`(`validate_kuku_a_value`、issue #208)を `a_value` 検証に呼ぶ。`command_type == 'pi'` の場合(issue #210)は同じ内部プレゼンテーション API を `generate_pi_problems`/`build_pi_slot_content_tex` で呼ぶほか、`backend/problem_generation.py`(`validate_pi_start`)を `a_value` 検証に呼ぶ(`validate_com_target` と対になる形で最初から共有バリデータとして抽出)。plain 2-term `ope` リクエスト(`_is_plain_ope_pdf_request` が真)の場合は同じ内部プレゼンテーション API を `generate_ope_problems`/`build_ope_slot_content_tex`(issue #205)で呼ぶほか、`backend/problem_generation.py` の ## 注意事項・既知の制限

- `nuts_calc_tex.py` 側のバリデーション失敗メッセージは `print()`(stdout)に出力されるため、`subprocess.CalledProcessError` ハンドラは `e.stdout` を優先し(空なら `e.stderr` にフォールバック)、それを `error` フィールドに含める(issue #37 で修正)。`nuts_calc.py`(issue #232 で削除)側でも `com`/`99`/`squ`/`pi`/`100` のバリデーション失敗が引数なし `exit()`(終了コード0、`subprocess.run(check=True)` が例外を送出しない)になっていた不具合を同 issue #37 で `exit(1)` に修正済みだった。修正前はこの経路で `CalledProcessError` すら発生せず、後続の `send_file` が `FileNotFoundError` になり実際の理由と無関係な「Renderer script not found」を返していた。
- backend の URL がフロントエンド側にハードコードされている(`frontend/web/src/catalog.js`・`preset.js`・`pcMakeFlow.js`・`presetDetail.js` それぞれの `API_BASE = 'http://127.0.0.1:5000'` の既知の制約。かつて併存していた `frontend/spa/src/CustomGenerator.jsx`/`GradeDrills.jsx` も同様の制約を持っていたが、`frontend/spa` 自体が issue #233 で削除された)。
- レンダラー選択は env 変数のみで、リクエストごとの指定はできない(issue #36 のスコープ)。`GET /renderer-info` はこの env 変数由来のレンダラー名をフロントエンドに公開する読み取り専用エンドポイントであり、フロントエンドからレンダラーを切り替える手段ではない。
- `command_type == 'com'`/`'lcm'`/`'99'`/`'pi'`、plain 2-term `ope`、`ope --use-parentheses`、かっこなし flat multi-term `ope`、および `squ` リクエストは、`nuts_calc_tex.get_latex_engine_adapter()` を `_generate_com_pdf`/`_generate_lcm_pdf`/`_generate_kuku_pdf`/`_generate_pi_pdf`/`_generate_ope_pdf`/`_generate_tree_ope_pdf`/`_generate_multi_term_ope_pdf`/`_generate_squ_pdf` から直接呼ぶため、`NUTS_CALC_TEX_ENGINE` 環境変数が不正な場合の失敗経路が他コマンドと異なる: 他コマンド(subprocess 経路)ではこの `ValueError` は CLI 側の `main()` 内で `failure()`(`exit(1)`)に変換され `CalledProcessError` として 500 になるが、これらの内部API経路では素の `ValueError` がそのまま 500 になる(いずれも HTTP 500 自体は同じだが `error` フィールドの文言が異なる)。環境設定ミス由来でリクエストごとに変動しないため許容している既知の差異(issue #199)。
- `com`/`lcm`/`99`/`pi`、plain 2-term `ope`、`ope --use-parentheses`、かっこなし flat multi-term `ope`、および `squ` は常に1ページ・blank(練習用)版のみを返す。`with_bottom_answer`/`with_name_field`/複数ページ(`page` > 1)/`merge`(`squ` はさらに `descend`/`shuffle`/`reverse` も)はそれぞれ `_generate_com_pdf`/`_generate_lcm_pdf`/`_generate_kuku_pdf`/`_generate_pi_pdf`/`_generate_ope_pdf`/`_generate_tree_ope_pdf`/`_generate_multi_term_ope_pdf`/`_generate_squ_pdf` に配線しておらず、リクエストに含めても無視される(issue #199/#211/#208/#205/#206/#207/#209/#210 のスコープ外。`#174`(B-5)の以降のコマンドグループ移行、またはそれぞれの追加スコープ issue で対応)。`99` は例外的に `descend`/`shuffle` だけは配線されている(`frontend/web` の `g2-kuku` プリセットが実際に送信するため、上記「動作の概要」の `_generate_kuku_pdf` 参照)。`pi` も `descend`/`shuffle` は配線されているが `reverse`(式の左右反転)は未配線(issue #210 のスコープ外)。
- `command_type == 'lcm'`/`'99'`/`'pi'` のルーティングは `_is_plain_ope_pdf_request` のような専用述語を介さず、`data.get('command_type') == 'lcm'`/`'99'`/`'pi'` の単純一致でそれぞれ `_generate_lcm_pdf`/`_generate_kuku_pdf`/`_generate_pi_pdf` へ無条件にディスパッチする(`com`/`squ` と同じ形)。`ope` と異なり `lcm`/`99`/`squ`/`pi` には別のコンテンツフォーマットパターンを要求するバリアントフラグ(`vertical`/`intermediate` 相当)が存在しないため、`ope` 系のような分岐述語は不要と判断した。
- plain 2-term `ope` の判定(`_is_plain_ope_pdf_request`)は `vertical`/`intermediate`/`use_parentheses`/`missing_value`/`terms`/`terms_min`/`terms_max`/`mixed_operators` のいずれかが指定されていれば内部API経路を使わず subprocess 経路にフォールバックする。`use_parentheses` は issue #206 で `_is_tree_ope_pdf_request` に切り出され、`vertical`/`intermediate`/`missing_value` のいずれも併用していなければ内部API経路(`_generate_tree_ope_pdf`)へルーティングされるようになった(`terms`系/`mixed_operators` は tree variant 自身の N項一般化として許容)。`terms`系(`use_parentheses` 非併用時)も issue #207 で `_is_multi_term_ope_pdf_request` に切り出され、`vertical`/`intermediate`/`use_parentheses`/`missing_value` のいずれも併用していなければ内部API経路(`_generate_multi_term_ope_pdf`)へルーティングされるようになった。残るのは `vertical`/`intermediate`/`missing_value`(`docs/latex/tex_content_format_taxonomy.md` 上で別のコンテンツフォーマットパターン5/6/2)のみで、これらは依然として subprocess 経路のまま。
